# Повторная сборка и смена VM

## Что сохраняется в GitHub

В репозитории находятся изменения устройства, patch, полный `source-manifest.xml` с закреплёнными revisions, инструменты подготовки и проверки. Это позволяет восстановить входные версии после смены VM. Полные Android checkout и `out/` не нужно добавлять в Git.

Для нового пустого рабочего каталога, после установки зависимостей из основного руководства:

```sh
bash scripts/prepare-server.sh /srv/infinity/android --locked
bash scripts/prepare-server.sh /srv/infinity/android --locked --sync --jobs 8
```

`--locked` использует static standalone manifest с абсолютными адресами remotes, а не новые вершины платформенных веток. Проверяются HEAD всех проектов, отсутствие посторонних изменений и совпадение итогового manifest. На повторном запуске допускается только точный unstaged patch устройства из набора. Как и при первой сборке, после подготовки нужны защита исходного дерева и запуск через проверяющий wrapper.

Режим проверен отдельной инициализацией Repo и загрузкой закреплённого commit небольшого проекта. Repo 2.71 при standalone-инициализации может выводить предупреждение про отсутствие Git HEAD у самого manifest — статический XML не является Git checkout. Проверять нужно итоговый exit status и ревизии; полный повторный cold-sync всех проектов на другой VM ещё не выполнялся.

## Что ускоряет следующую сборку

- Если нужен тот же опубликованный результат, его скачивают повторно: компиляция не требуется.
- Для небольших изменений сохранённый `/srv/infinity/out` позволяет системе сборки переиспользовать подходящие промежуточные результаты.
- На чистой VM без такого каталога сборка снова будет полной. Наличие готового ZIP не заменяет промежуточные результаты.
- Отдельный compiler cache полезен только при поддержке конкретной сборочной системой; его наличие и результативность надо проверять, а не предполагать.

Для быстрой миграции сохранить отдельный диск/снимок или архив с checkout и `out/`. Если сохраняется только `out/`, исходники восстанавливаются по `--locked`. Сохранять те же абсолютные пути, архитектуру x86-64 и совместимое окружение. Архивы и их SHA-256 должны происходить из доверенного завершённого задания; неизвестный cache может подменить результаты даже при неизменных исходниках.

Сейчас отдельное платное хранилище не создано. До удаления старой VM необходимо решить, где останется диск/backup; иначе ускоряющие промежуточные файлы будут потеряны. GitHub не является резервной копией всего сборочного диска.

## Публикация результатов

Планируемый процесс: ручной запуск владельцем → подтверждение окружения `build-vm` → сборка на VM → проверка исходников/образов → GitHub prerelease с SHA-256, source manifest, описанием известных проблем и ссылкой на реальный Actions run.

Текущая первая сборка запущена через SSH и не должна обозначаться как выполненная GitHub Actions. Actions пока выключены, runner не подключён, автоматическая публикация ещё не настроена. Нельзя публиковать повреждённый или не прошедший проверки результат как успешный. Для прошивки без аппаратных испытаний указывать экспериментальный статус явно.

В GitHub Releases один файл должен быть меньше 2 GiB; размер реального OTA надо проверить до выбора способа публикации. Большой cache нельзя смешивать с пользовательскими firmware-артефактами.
