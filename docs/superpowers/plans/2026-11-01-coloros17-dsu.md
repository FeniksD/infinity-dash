# ColorOS 17 DSU preparation implementation plan

> Execution: inline in this session under the user's explicit instruction to work on ColorOS. Use the existing reviewed acquisition/audit helpers where sufficient. Do not start another Android source build.

**Goal:** Produce a traceable first ColorOS17 DSU candidate from official OPPO input without replacing the owner's working Infinity installation.

**Architecture:** Acquire and inspect the signed donor separately from the port transformations. Run a pinned, reviewed Mystic-based pipeline under an unprivileged build account. Build a separate candidate image; later file deltas apply to the inactive DSU copy and to its canonical host tree.

**Tech stack:** Python3, ZIP/payload parsers, pinned MysticGSI, ext4/AVB tools, ADB and Android DSU.

**Spec:** `docs/superpowers/specs/2026-11-01-coloros17-dsu-design.md`

## Global constraints

- Device `dash`; donor must report ColorOS17 / SDK37.
- Manufacturer-origin firmware only; no third-party GSI used as the base.
- Preserve LK, bootloader, modem/NV/eSIM, working Infinity and its data.
- No inherited unconditional permissive SELinux, insecure ADB, opaque hex patch or bulk debloat.
- No phone write until the exact candidate and recovery boundaries have been reviewed.

## Review focus

- Missing/malformed/wrong-SDK profiles must abort before any tree mutation.
- Self-contained partial OTAs must be distinguished from source-dependent deltas.
- SDK36 fallback must not silently masquerade as a ColorOS17 profile.
- Stock APK/file retention must not lose owner/mode/capabilities/SELinux metadata during partition merging.
- EXT4 edits must not be called safe while mounted, on the wrong DSU slot, or with unresolved AVB protection.

## Task 4: Build and validate a DSU candidate

- [ ] Build raw EXT4 with deliberate free space for later file edits and a documented AVB policy.
- [ ] Validate filesystem, image size, paths/labels, Android/ColorOS version and digest.
- [ ] Review candidate scope, remaining risks and rollback path before any phone write.
- [ ] After device authorization/readiness, import once through DSU and capture boot logs and core hardware results.

## Task 5: Add file-only iterations after the first boot

- [ ] Identify and verify the exact inactive DSU instance, filesystem and mapping before editing.
- [ ] Test refusal of active/wrong-build targets, changed input hashes, insufficient space and unsupported verification state.
- [ ] Use a small patch manifest with preserved metadata, transactional backup and idempotent rollback.
- [ ] Apply matching deltas to the canonical host tree and prove a later full image includes them.
