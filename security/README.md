# Контроль сборочного сервера

Это сигнализация изменений с приостановкой сборки, а не гарантия отсутствия взлома. Она не может аттестовать уже скомпрометированные root/kernel или инфраструктуру провайдера.

`guard.py` запускается от root таймером systemd каждую минуту. Он сверяет SHA-256, типы, владельцев и права защищённых файлов; состав каталогов; новые службы и слушающие сокеты; новые успешные SSH-входы; активность firewall. Предъявление ключа до аутентификации не считается успешным входом. Изменение обнаруживается даже после удаления учётной записи сборщика: UID сборочных процессов закреплён как **1000** для этой VM.

При отклонении сохраняется первая причина в `/var/lib/infinity-guard/incident.json`, обновляется `status.json`, а процессы UID 1000 получают SIGSTOP. Если пауза не удалась, статус явно сообщает это. Возобновления автоматически нет. Следующие ошибки не затирают первую причину.

`local_monitor.py` на ПК каждые 60 секунд получает байты подготовленного набора по SSH и сверяет их с локальным архивом. Ожидаемые права учитывают намеренное удаление записи для группы и остальных пользователей; появление такой записи на сервере остаётся тревогой. Он также проверяет точное совпадение серверного эталона с локальной копией и свежесть состояния серверной сигнализации. Неисправность проверки и повреждение входных файлов дают тревогу; тревога переживает перезапуск процесса. Пока ПК выключен, эта дополнительная сверка недоступна, серверный таймер продолжает работать.

Защищаются настройки SSH/firewall, ключи доступа, системные учётные записи, локальные unit/cron-конфигурации, инструменты контроля и исходный набор подготовки. После завершения `repo sync` нужен отдельный этап: сохранить resolved manifest и проверить содержимое Android-исходников, зафиксировать их эталон перед компиляцией. Сборочные результаты и логи изменяются штатно и не должны сравниваться с исходниками.

Сначала устанавливаются и включаются unit-файлы **без запуска** таймера; затем после сверки файлов создаётся эталон, его копия сохраняется локально, выполняется ручная проверка и только после неё запускается таймер. Не создавать новый эталон, чтобы убрать необъяснённую тревогу. После подтверждённого намеренного изменения нужны сверка локального diff и обновление обеих копий. Тревоги сохранять отдельно перед ручным возобновлением.

Полный мониторинг гипервизора, консоли/VNC в панели облака и безопасности аккаунта провайдера изнутри VM невозможен. Входы в саму VM и её службы — отдельная область проверки.
