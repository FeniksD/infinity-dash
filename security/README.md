# Контроль сборочного сервера

Это сигнализация изменений с приостановкой сборки, а не гарантия отсутствия взлома. Она не может аттестовать уже скомпрометированные root/kernel или инфраструктуру провайдера.

`guard.py` запускается от root таймером systemd каждую минуту. Он сверяет SHA-256, типы, владельцев и права защищённых файлов; состав каталогов; новые службы и слушающие сокеты; новые успешные SSH-входы; активность firewall. Предъявление ключа до аутентификации не считается успешным входом. Изменение обнаруживается даже после удаления учётной записи сборщика: UID сборочных процессов закреплён как **1000** для этой VM.

При отклонении сохраняется первая причина в `/var/lib/infinity-guard/incident.json`, обновляется `status.json`, а процессы UID 1000 получают SIGSTOP. Если пауза не удалась, статус явно сообщает это. Возобновления автоматически нет. Следующие ошибки не затирают первую причину.

`local_monitor.py` на ПК каждые 60 секунд получает байты подготовленного набора по SSH и сверяет их с локальным архивом. Ожидаемые права учитывают намеренное удаление записи для группы и остальных пользователей; появление такой записи на сервере остаётся тревогой. Он также проверяет точное совпадение серверного эталона с локальной копией и свежесть состояния серверной сигнализации. Неисправность проверки и повреждение входных файлов дают тревогу; тревога переживает перезапуск процесса. Пока ПК выключен, эта дополнительная сверка недоступна, серверный таймер продолжает работать.

При распознанном транспортном сбое SSH разрешены три повторные полные проверки с задержками 3, 7 и 10 секунд. Это до 20 секунд дополнительных ожиданий плюс обычные ограниченные таймауты SSH; серверный контроль всё это время продолжает работать. Несовпадение файлов/эталона, ошибка ключа хоста или авторизации, несвежий/неисправный серверный контроль не получают таких повторов. Если связь не восстановилась, тревога фиксируется и сборка останавливается; последующее восстановление связи не снимает блокировку автоматически. Причина тревоги сохраняется и после последующих успешных сверок до ручного разбора.

Защищаются настройки SSH/firewall, ключи доступа, системные учётные записи, локальные unit/cron-конфигурации, инструменты контроля и исходный набор подготовки. После завершения `repo sync` нужен отдельный этап: сохранить resolved manifest и проверить содержимое Android-исходников, зафиксировать их эталон перед компиляцией. Сборочные результаты и логи изменяются штатно и не должны сравниваться с исходниками.

`source_lock.py` формирует потоковый SHA-256 manifest файлов и ссылок после закрытия дерева от записи. Он отклоняет внешние ссылки, ссылки в исключённые `.repo`/`.git`/`out`/логи и hardlinks. Исходное дерево становится собственностью root, а сборщик не получает права записи даже через альтернативный путь к тем же inode. Read-only bind закрывает исходный путь; отдельный writable bind используется только для логов. Проверяются совпадение настоящего каталога логов и отсутствие неожиданных writable подмонтирований.

Узкое исключение перечислено в `source-link-policy.json`: три ссылки для упаковки systemd-сервисов образа Google Trout. Их исходные тексты сверены с закреплёнными Git-объектами. Разрешается только точная пара путь/цель, цель должна отсутствовать на сборочной VM, а все существующие каталоги на пути к ней должны принадлежать root и быть недоступны для записи группе/остальным. Политика включается в manifest и сверяется повторно. Произвольные внешние ссылки и ссылки в writable-логи остаются запрещены.

`build_guarded.sh SOURCE MANIFEST OUTPUT LOGS` проверяет режим mount и все входные файлы до и после вызова сборки, запрещает запуск от root и размещение результатов внутри исходников. Эта проверка дополняет периодический контроль; интервал в минуту сам по себе не исключает быструю подмену с восстановлением.

Для совместимости Siso/Soong логический `OUT_DIR=out` является проверяемым bind mount внешнего `OUTPUT`. Физически результаты остаются вне исходников. Внутри исходного mount разрешены только две ожидаемые writable-точки: `out` и `.infinity-dash-logs`; их связь с внешними каталогами также контролируется. Ссылки исходников в эти каталоги не разрешены.

Сначала устанавливаются и включаются unit-файлы **без запуска** таймера; затем после сверки файлов создаётся эталон, его копия сохраняется локально, выполняется ручная проверка и только после неё запускается таймер. Не создавать новый эталон, чтобы убрать необъяснённую тревогу. После подтверждённого намеренного изменения нужны сверка локального diff и обновление обеих копий. Тревоги сохранять отдельно перед ручным возобновлением.

Полный мониторинг гипервизора, консоли/VNC в панели облака и безопасности аккаунта провайдера изнутри VM невозможен. Входы в саму VM и её службы — отдельная область проверки.

## Запуски через GitHub

Публичный репозиторий используется для исходников и портфолио. Actions выключены, workflows и подключённые self-hosted runners отсутствуют. Для будущей интеграции создано окружение `build-vm` с обязательным подтверждением FeniksD и разрешённой веткой `main`.

Перед включением автоматизации сборочный job должен использовать это окружение, только ручной `workflow_dispatch`, проверку постоянного ID владельца и инициатора повторного запуска. Не запускать сборку от событий pull request, issue, fork, push или schedule. Проверка внутри изменяемого workflow сама по себе не защищает от администратора, способного переписать workflow; доступ к репозиторию и аккаунту остаётся частью границы доверия. VM пока не подключена к GitHub Actions.
